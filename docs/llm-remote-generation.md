# Генерация ответов LLM локально при бэкенде на хостинге

## Проблема

Генерация ответа на вопрос о товаре происходит **внутри бэкенда** (`src/opencode/opencode.service.ts`):

- `localLLM()` дёргает `llama-server` на `http://localhost:8080/v1/chat/completions` (`src/opencode/opencode.service.ts:6`);
- `checkLocalLLM()` сам спавнит `/opt/homebrew/bin/llama-server` и убивает его по таймауту простоя (`src/opencode/opencode.service.ts:57`);
- `opencodeLLM()` вызывает CLI `opencode run ...` через `execSync` (`src/opencode/opencode.service.ts:137`).

На хостинге нельзя ни то, ни другое: нет macOS-путей, нет GPU, нет `opencode` в PATH, поднимать модель на сервере дорого.

Запускать админку локально **не поможет**: админка обращается к бэкенду, а запрос к LLM уходит из бэкенда. Задача всегда одна — дать бэкенду на хостинге сетевой путь к локальной LLM.

```
Админка (хостинг) ──► Бэкенд NestJS (хостинг) ──► ??? ──► LLM (моя машина)
```

## Обзор решения из интернета

Проверено, что задача типичная и решения есть.

| Подход | Суть | Вердикт |
| --- | --- | --- |
| **Cloudflare Tunnel** (`cloudflared tunnel --url http://localhost:8080`) | Исходящие соединения с вашей машины к инфраструктуре Cloudflare, наружу — HTTPS-домен. Входящих портов открывать не нужно | Стандартное решение для «выставить локальную LLM наружу». Quick Tunnel — для теста (домен меняется, нет SSE, ≤200 одновременных запросов). Продакшен — именованный туннель + Cloudflare Access (service token) |
| **SSH reverse tunnel / frp / Tailscale** | На сервере: `ssh -R 8080:localhost:8080 user@vps`, бэкенд ходит в `127.0.0.1:8080` | Проще по коду, но нужен SSH-доступ к VPS и чтобы туннель был поднят |
| **Cloudflare Access service token** | Серверный HTTP-клиент шлёт `CF-Access-Client-Id` + `CF-Access-Client-Secret`, endpoint закрыт для всех остальных | Обязательная часть для варианта A: публичный endpoint с LLM без авторизации — это открытый бесплатный генератор для всех желающих |
| **LiteLLM Proxy** | Self-hosted OpenAI-совместимый шлюз: 100+ провайдеров за одним `/v1/chat/completions`, virtual keys, авто-фолбэк на резервную модель | Готовый «фолбэк-механизм»: локальная LLM через туннель как первый маршрут, облако как запасной |
| **Очередь задач + локальный воркер** | Сервер кладёт промпт в БД; локальный скрипт забирает, генерирует, возвращает результат | Нужна разработка, но **в этом репозитории паттерн уже реализован** — см. `src/sms/sms.service.ts:111` и `docs/sms-module.md` |
| **OpenCode Zen API** | HTTP-API с бесплатными моделями (`big-pickle`, `space-bunny-free`, `ling-3.1-flash-free`, …), endpoint `https://opencode.ai/zen/v1/chat/completions` | Готовый вариант «вообще без локальной машины» и естественный фолбэк |

Готового «коробочного» решения именно под генерацию ответов для магазина нет — есть только транспортные примитивы (туннели, шлюзы). Дальше выбираем транспорт.

## Обязательный этап 0 — рефакторинг `OpenCodeService`

Нужен для **обоих** вариантов, иначе код сломается на хостинге. Сейчас в сервисе хардкод macOS-путей и портов, автозапуск модели и `execSync` без таймаута.

### 0.1 Конфигурация через env

Все параметры — в `ConfigService` (в проекте уже есть `ConfigModule.forRoot({ isGlobal: true })`, `src/app/app.module.ts:73`). Добавить:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `LLM_TRANSPORT` | `local` | `local` \| `tunnel` \| `queue` \| `opencode` \| `cloud` — какой транспорт активен |
| `LLM_BASE_URL` | `http://localhost:8080` | адрес OpenAI-совместимого эндпоинта |
| `LLM_HEALTH_URL` | `http://127.0.0.1:8080/health` | адрес health-check |
| `LLM_MODEL` | `gemma-4-E2B_q4_0-it` | имя модели |
| `LLM_API_KEY` | — | bearer для Zen/туннеля с Access |
| `LLM_TIMEOUT_MS` | `120000` | таймаут запроса |
| `LLM_AUTOSTART` | `true` в dev, `false` в прод | спавнить ли `llama-server` |
| `LLAMA_BIN` | `/opt/homebrew/bin/llama-server` | путь к бинарю |
| `LLAMA_MODEL_PATH` | `/Users/i-mobi/llm-models/…gguf` | путь к gguf |

`llama-server`, модель, порт уезжают из кода в `.env`. На хостинге `LLM_AUTOSTART=false` и пути не нужны вовсе.

### 0.2 Разделить интерфейс и транспорты

`OpenCodeService` превращается в фасад над стратегиями, чтобы `ProductQuestionService` (`src/product-question/product-question.service.ts:224`) не знал, откуда придёт ответ:

```
LlmClient (интерфейс)
├── LocalLlamaClient     — llama-server на localhost (dev)
├── TunneledLlamaClient  — llama-server через туннель (вариант A)
├── OpenCodeCliClient    — CLI opencode (dev/фолбэк)
├── CloudLlmClient       — OpenAI-совместимый облачный API (Zen и т.п.)
└── QueueLlmClient       — постановка в llm_outbox и ожидание (вариант B)
```

`OpenCodeService.query()` остаётся фасадом и переключает транспорт по `LLM_TRANSPORT`. На хостинге при `LLM_TRANSPORT=tunnel` код веток про macOS и `opencode` не выполняется вовсе.

### 0.3 Технические долги, которые сломают прод

| Проблема | Где | Что сделать |
| --- | --- | --- |
| Нет таймаута на `fetch` → при поднятом туннеле и грузящейся модели HTTP-запрос админки висит | `src/opencode/opencode.service.ts:25` | `AbortSignal.timeout(LLM_TIMEOUT_MS)` |
| `spawn` без обработки отсутствующего бинаря | `src/opencode/opencode.service.ts:69` | только при `LLM_AUTOSTART=true` |
| `execSync` блокирует event loop на всё время генерации | `src/opencode/opencode.service.ts:158` | заменить на `execFile`/`spawn` с промисом; в проде этот путь выключен |
| Health-check на каждый запрос | `src/opencode/opencode.service.ts:13` | кэш результата на 10–15 сек + circuit breaker |
| `checkLocalLLM` бросает исключение при занятом порте вместо возврата статуса | `src/opencode/opencode.service.ts:67` | возвращать статус, ошибки — наружу в одном месте |
| Нет ретраев и лимита длины ответа | — | ретрай 1–2 раза, обрезка ответа до 1000 символов под `answer` |

## Вариант A — туннель (рекомендуется начать с него)

Суть: локальная LLM остаётся обычным OpenAI-совместимым эндпоинтом, но доступна снаружи. Бэкенд на хостинге ходит в неё по HTTPS. **Админка, контроллер, DTO и синхронный ответ не меняются вообще** — меняется только адрес из env.

### Схема

```
Админка ──► Бэкенд (хостинг) ──HTTPS──► Cloudflare ──► cloudflared (моя машина) ──► llama-server :8080
                 + CF-Access-Client-Id / Secret
```

### Шаги

1. **Локально**: поднять `llama-server` на `0.0.0.0:8080` (не только `127.0.0.1`).
2. **Локально**: установить `cloudflared`.
3. **Тест (5 минут)**: `cloudflared tunnel --url http://localhost:8080` → получить `https://xxx.trycloudflare.com`.
   - `curl https://xxx.trycloudflare.com/health` с чужой машины;
   - `curl -X POST https://xxx.trycloudflare.com/v1/chat/completions -d '{...}'` — убедиться, что генерация идёт.
4. **Продакшен-туннель**: завести именованный туннель в дашборде Cloudflare (постоянный домен, SLA вместо «нет гарантии uptime»), направить на `localhost:8080`.
5. **Закрыть доступ**: перед туннелем поставить Cloudflare Access и выдать service token. Токен положить в `.env` хостинга как `LLM_API_KEY`. Без этого любой, кто угадает домен, получит бесплатный LLM.
6. **Бэкенд**: `LLM_TRANSPORT=tunnel`, `LLM_BASE_URL=https://<домен>/v1/chat/completions`, `LLM_API_KEY=<CF-Access secret>`, `LLM_AUTOSTART=false`.
7. **Проверить**: `POST /product-question/generate-answer` с хостинга возвращает сгенерированный ответ.

### Плюсы и минусы

Плюсы: минимальная работа в коде, нет изменений в админке, ответ синхронный, низкая задержка.
Минусы: машина и туннель должны быть запущены в момент генерации; при выключенной машине генерация невозможна (до подключения фолбэка из варианта C); зависимость от внешнего сервиса Cloudflare.

### Что выбрать между Cloudflare и SSH

| | Cloudflare Tunnel | SSH reverse tunnel |
| --- | --- | --- |
| Нужен доступ к VPS | нет | да |
| Входящие порты | не нужны | не нужны |
| Домен | постоянный (именованный туннель) | локальный `127.0.0.1` |
| Авторизация запросов | Access service token | только по SSH-ключу, свой токен писать руками |
| Требует внешний сервис | да | нет |

Выбор сводится к наличию SSH-доступа к VPS.

## Вариант B — очередь задач + локальный воркер

Суть: бэкенд не ждёт ответа, а создаёт задачу в БД. Отдельный процесс на вашей машине забирает задачи, генерирует локально и возвращает результат. Админка опрашивает статус.

### Схема

```
Админка ──► Бэкенд (хостинг): POST generate-answer ──► llm_outbox (status=pending) ──► { job_id }
   │                                                                                        │
   └──── GET job/:id каждые 2 сек ◄─── результат ◄─── воркер (моя машина) ◄── GET llm/outbox
```

### Почему это легко именно здесь

В репозитории уже есть работающий образец: модуль SMS — приложение на телефоне владельца поллит `GET /sms/outbox`, забирает задачу и отвечает `POST /sms/outbox-delivered/:id`. Атомарный захват сделан через транзакцию с `pessimistic_write` + `skip_locked` (`src/sms/sms.service.ts:117`). LLM-очередь делается по той же схеме, меняется только наполнение задачи.

### Сущность `llm_outbox`

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | int | PK |
| `product_id` | int? | товар (для логов и ручной проверки) |
| `question_id` | int? | вопрос, если генерация привязана к конкретному вопросу |
| `prompt` | text | готовый промпт (собирается на хостинге — секреты товара наружу не уходят) |
| `status` | varchar | `pending` \| `in_work` \| `done` \| `failed` |
| `result` | varchar? | сгенерированный текст ответа |
| `error_reason` | varchar? | причина ошибки от воркера |
| `attempts` | int | число попыток |
| `worker_id` | varchar? | кто брал (для ретрая тем же воркером, как в SMS) |
| `created_at` / `updated_at` | timestamp | TTL считается от `updated_at` |

Промпт собирается на хостинге (`ProductQuestionService` уже формирует его в `generateAnswer`) — на машину уходит только текст, обратно приходит только ответ.

### Эндпоинты

| Метод | Доступ | Описание |
| --- | --- | --- |
| `POST /product-question/generate-answer` | admin/moderator | создаёт задачу, возвращает `{ job_id, status: 'pending' }` |
| `GET /product-question/generate-answer/:job_id` | admin/moderator | статус задачи и результат |
| `GET /llm/outbox` | service-token | воркер забирает **одну** задачу или `null` |
| `POST /llm/outbox/:id/done` | service-token | результат |
| `POST /llm/outbox/:id/failed` | service-token | ошибка + `error_reason`, запись остаётся ретраябельной |

Эндпоинты `/llm/*` защищаются общим токеном из env (отдельный guard, не `@Public()` как в SMS — там была не сделана аутентификация устройств, здесь её нужно сделать сразу).

### Локальный воркер

Отдельный Node-скрипт (например `tools/llm-worker/`, вне `src/`):

- цикл: `GET /llm/outbox` → если задача есть, вызвать локальную `llama-server` (или `opencode run`) → `POST /llm/outbox/:id/done`;
- пауза между опросами 2–5 сек при пустой очереди;
- автозапуск/остановка `llama-server` переиспользовать из текущего `checkLocalLLM` — с теми же аргументами;
- ретрай: `POST /llm/outbox/:id/failed` — задача возвращается в очередь для другого/следующего прохода;
- пережить рестарт: если машина выключилась посреди генерации, зависшая `in_work` возвращается в `pending` по TTL.

### Плюсы и минусы

Плюсы: работает без открытых портов и без внешних сервисов, только исходящие запросы с машины; очередь переживает рестарты обеих сторон; можно накопить 50 вопросов и разом сгенерировать; расширяется на другие LLM-сценарии.
Минусы: нужно писать код в бэкенде, воркер и правку админки (поллинг вместо одного ответа); ответ приходит не сразу; больше мест, где что-то может зависнуть.

## Вариант C — фолбэк в облако

Нужен, чтобы генерация не умирала, когда машина выключена. Реализуется как ещё один `LlmClient` в варианте 0.2 + circuit breaker.

- Endpoint: `https://opencode.ai/zen/v1/chat/completions`.
- Бесплатные модели: `big-pickle`, `space-bunny-free`, `ling-3.1-flash-free`, `longcat-2.5-preview-free`, `fledge-alpha-free`, `nemotron-3.5-lightning-free`.
- Авторизация: `Authorization: Bearer $OPENCODE_API_KEY`.
- Порядок выбора: локальная/туннельная LLM → при таймауте или ошибке облако. Либо по флагу: `LLM_FALLBACK=cloud`.
- ⚠️ Данные товара уходят провайдеру. У части моделей zero-retention, у `big-pickle` во время бесплатного периода данные могут использоваться для улучшения модели. Если это неприемлемо — вариант C не включать, а полагаться на B.

## Сравнение

| Критерий | A: туннель | B: очередь | C: облако |
| --- | --- | --- | --- |
| Работа в коде | ~30 строк конфига | новая сущность, 5 эндпоинтов, воркер, правка админки | ~50 строк, один клиент |
| Синхронный ответ | да | нет (поллинг) | да |
| Работает при выключенной машине | нет | нет (задача ждёт) | да |
| Нужны открытые порты | нет | нет | нет |
| Зависимость от внешнего сервиса | Cloudflare | нет | провайдер LLM |
| Устойчивость к обрывам | туннель рвётся — ошибка пользователю | очередь переживает всё | у провайдера есть лимиты |

## Рекомендация

Порядок внедрения: **A → C → B (по необходимости)**.

Шаг 1 — рефакторинг (этап 0). Без него ни один вариант не заработает на хостинге: macOS-пути и `execSync` без таймаута.

Шаг 2 — вариант A. Даёт рабочую локальную LLM на проде за час и не трогает админку. Если туннель по какой-то причине не поднимется — выяснится это сразу и дёшево.

Шаг 3 — вариант C как фолбэк, чтобы админка не получала ошибку при выключенной машине. Решается флагом.

Шаг 4 — вариант B, только если появится реальная потребность: офлайн-накопление вопросов, пакетная генерация, или запрет на передачу данных наружу (тогда C исключается и B становится единственным способом).
