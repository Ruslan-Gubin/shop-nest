# Модуль отправки SMS (outbox)

## Идея

SMS со стороны бекенда не отправляются — этим занимается **отдельное приложение на телефоне владельца** (телефон постоянно онлайн). Приложение каждые ~5 секунд поллит бекенд: «есть ли сообщение на отправку?». Если есть — отправляет SMS и сообщает бекенду результат (успех/ошибка).

Для этого в БД хранится очередь записей (`sms_outbox`). Одна запись = одна SMS (код подтверждения).

## Жизненный цикл записи

```
pending ──(устройство забрало)→ in_work ──(отправлено)→ delivered ──(verify-otp)→ запись удаляется
   │                              │
   └──(никто не берёт, TTL 5 мин)─┴──(ошибка отправки)→ failed* ──(другое устройство)→ in_work → ...
```

- `pending` — ждёт, пока устройство возьмёт её в работу
- `in_work` — устройство взяло и сейчас отправляет
- `delivered` — успешно отправлено, код действителен до TTL
- `failed` / `failed_no_balance` / `failed_invalid_number` / `failed_gateway` — ошибка отправки; запись **остаётся в очереди** и может быть взята в работу другим устройством (ретрай)

## Флоу входа по телефону

1. Клиент (мобильное/веб приложение) → `POST /sms/request-otp { phone, device_id? }`
   - проверка rate limit (не чаще 1 SMS в 60 сек на связку phone/device_id)
   - генерация 6-значного кода, сохранение в `sms_outbox` (статус `pending`, TTL 5 мин)
2. Приложение-отправитель → `GET /sms/outbox?sender_phone=<номер устройства>` каждые ~5 сек
   - сервер находит **одну** подходящую запись: `pending` или ошибку `failed*`, где номер устройства ещё не в `sender_phones`
   - захват атомарный: статус → `in_work`, номер устройства добавляется в массив `sender_phones`
   - если подходящих записей нет — ответ `data: null`
3. Устройство отправляет SMS с текстом из `message_text`:
   - успех → `POST /sms/outbox/:id/delivered` — статус `delivered`
   - ошибка → `POST /sms/outbox/:id/failed { error_code?, error_reason? }` — статус ошибки + причина
4. Пользователь вводит код → `POST /auth/verify-otp { phone, code }`
   - проверка кода делегируется `SmsService.verifyOtp` (hash, срок, лимит попыток, одноразовость)
   - пользователь найден по телефону → вход; не найден → создаётся новый пользователь
   - выдача токенов

### Ретрай ошибок

Устройство, чей номер уже есть в `sender_phones` записи, не может взять её повторно (даже если она в статусе ошибки) — этим исключается повторная отправка тем же устройством. Ретрай делает **другое** устройство: при каждом новом взятии номер добавляется в `sender_phones`.

```json
// пример: +7123 отправляло и упало по балансу, +7456 забрало на ретрай
"sender_phones": ["+71234567890", "+74567890123"]
```

## Сущность `sms_outbox`

| Поле               | Тип      | Назначение                                            |
| ------------------ | -------- | ----------------------------------------------------- |
| `id`               | int      | PK                                                     |
| `phone`            | varchar  | телефон получателя (строка цифр, как пришёл)           |
| `code_hash`        | varchar  | argon2-хэш 6-значного кода                             |
| `message_text`     | varchar  | готовый текст SMS (содержит код)                       |
| `status`           | varchar  | `pending \| in_work \| delivered \| failed*`           |
| `delivery_attempts`| int      | неудачные попытки доставки устройством                |
| `verify_attempts`  | int      | неудачные вводы кода пользователем (лимит 5)           |
| `sender_phones`    | text[]   | номера устройств, бравших запись (для исключения ретрая тем же устройством) |
| `error_reason`     | varchar  | детализация ошибки от устройства                      |
| `device_id`        | varchar? | uuid клиента (localStorage) для rate limit             |
| `created_at`       | timestamp|                                                       |
| `updated_at`       | timestamp| (исходная точка TTL 5 мин: протухшие записи удаляются в `sms/outbox`) |

## Эндпоинты модуля `sms`

| Метод                            | Доступ | Описание                                          |
| -------------------------------- | ------ | ------------------------------------------------- |
| `POST /sms/request-otp`          | public | клиент запросил код → генерация и запись в очередь |
| `GET /sms/outbox?sender_phone=`  | public | устройство забирает **одну** задачу или `null`    |
| `POST /sms/outbox/:id/delivered` | public | отправлено успешно → статус `delivered`           |
| `POST /sms/outbox/:id/failed`    | public | ошибка → статус ошибки + `error_reason`           |

Роут `POST /auth/verify-otp` (модуль `auth`) проверяет код через `SmsService.verifyOtp`, затем находит/создаёт пользователя и выдаёт токены. Всё, что связано с SMS/кодом/устройством, живёт в `sms`; `auth` о механике отправки не знает.

> ⚠️ Пока аутентификация устройства-отправителя не реализована (роуты public, `sender_phone` просто валидируется как номер). В будущем: в админке указываются разрешённые телефоны отправителей, `GET /sms/outbox` сверяет `sender_phone` с этим списком.

## Коды ошибок устройства (body `POST /outbox/:id/failed`)

| `error_code`           | Статус записи            |
| ---------------------- | ------------------------ |
| `no_balance` / `insufficient_balance` | `failed_no_balance` |
| `invalid_number` / `invalid_recipient` | `failed_invalid_number` |
| `gateway` / `network` / `timeout` | `failed_gateway` |
| любой другой / пусто   | `failed`                |

`error_reason` — произвольное текстовое описание от устройства (до 500 символов).

## Лимиты и безопасность

- Код: 6 цифр, TTL 5 мин (от `updated_at`), в ответе API не возвращается (только в тексте SMS). Протухшие записи удаляются при каждом опросе `GET /sms/outbox` и не отдаются в работу.
- `verify_attempts`: 5 неудачных вводов → код становится недействительным. Пользователь **не блокируется навсегда** — он запрашивает новый код (новая SMS).
- `delivery_attempts`: счётчик неудач; растёт при каждой ошибке. Запись со статусом ошибки остаётся ретраябельной, пока её берут новые устройства.
- Rate limit на `request-otp`: не чаще 1 SMS в 60 сек на связку `phone` / `device_id`. Защищает от спама по чужим номерам (каждая запись = реальная SMS владельца устройства). Лимит N SMS/час — отложен до прод-стадии.

## Идентификация устройства клиента

В `request-otp` пользователь ещё не авторизован, поэтому бекенд не может надёжно определить устройство/пользователя. Принятое решение: клиент один раз генерирует `uuid`, хранит в `localStorage` и шлёт его в теле запроса полем `device_id`. Бекенд использует его (вместе с `phone`) для rate limit.
