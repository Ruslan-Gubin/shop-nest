# Модуль отправки SMS (outbox)

## Идея

SMS со стороны бекенда не отправляются — этим занимается **отдельное приложение на телефоне владельца** (телефон постоянно онлайн). Приложение каждые ~10 секунд поллит бекенд: «есть ли сообщения на отправку?». Если есть — отправляет SMS и сообщает бекенду, что сообщение доставлено.

Для этого в БД хранится очередь записей (`sms_outbox`). Запись живёт в статусе `pending`, после успешной отправки устройством — **удаляется**.

## Флоу входа по телефону

1. Клиент (мобильное/веб приложение) → `POST /sms/request-otp { phone, device_id? }`
   - проверка rate limit (см. ниже)
   - генерация 6-значного кода, сохранение в `sms_outbox` (статус `pending`, TTL 5 мин)
2. Приложение-отправитель → `GET /sms/outbox?phone=<номер устройства>` каждые ~10 сек
   - получает список `pending` записей (только не протухшие), к себе привязывается `sender_phone`
3. Устройство отправляет SMS с текстом из `message_text` → `POST /sms/outbox/:id/delivered`
   - запись **удаляется**
4. Пользователь вводит код → `POST /auth/verify-otp { phone, code }`
   - проверка кода делегируется `SmsService.verifyOtp` (hash, срок, лимит попыток, одноразовость)
   - пользователь найден по телефону → вход; не найден → создаётся новый пользователь
   - выдача токенов

Админка продолжает входить по email + паролю через существующие `sign-in` / `sign-up`.

## Сущность `sms_outbox`

| Поле               | Тип      | Назначение                                            |
| ------------------ | -------- | ----------------------------------------------------- |
| `id`               | int      | PK                                                     |
| `phone`            | varchar  | телефон получателя (нормализован, E.164)               |
| `code_hash`        | varchar  | argon2-хэш 6-значного кода                             |
| `message_text`     | varchar  | готовый текст SMS (содержит код)                       |
| `status`           | varchar  | `pending \| delivered \| failed`                       |
| `delivery_attempts`| int      | попытки доставки устройством (лимит 3 → `failed`)      |
| `verify_attempts`  | int      | неудачные вводы кода пользователем (лимит 5)           |
| `sender_phone`     | varchar? | номер телефона устройства, забравшего запись           |
| `device_id`        | varchar? | uuid клиента (localStorage) для rate limit             |
| `expires_at`       | timestamp| когда код протухает (5 мин)                            |
| `created_at`       | timestamp|                                                       |
| `updated_at`       | timestamp|                                                       |

## Эндпоинты модуля `sms`

| Метод                            | Доступ | Описание                                          |
| -------------------------------- | ------ | ------------------------------------------------- |
| `POST /sms/request-otp`          | public | клиент запросил код → генерация и запись в очередь |
| `GET /sms/outbox?phone=`         | public | список `pending` записей для устройства-отправителя |
| `POST /sms/outbox/:id/delivered` | public | устройство отправило → запись удаляется            |
| `POST /sms/outbox/:id/failed`    | public | ошибка доставки → `delivery_attempts+1`            |

Роут `POST /auth/verify-otp` (модуль `auth`) проверяет код через `SmsService.verifyOtp`, затем находит/создаёт пользователя и выдаёт токены. Всё, что связано с SMS/кодом/устройством, живёт в `sms`; `auth` о механике отправки не знает.

> ⚠️ Пока аутентификация устройства-отправителя не реализована (роуты public, отдаются только не-протухшие `pending`). В будущем: в админке указываются разрешённые телефоны отправителей, `GET /sms/outbox` сверяет `phone` с этим списком.

## Лимиты и безопасность

- Код: 6 цифр, `expires_at` = +5 мин, в ответе API не возвращается (только в тексте SMS).
- `verify_attempts`: 5 неудачных вводов → код становится недействительным. Пользователь **не блокируется навсегда** — он запрашивает новый код (новая SMS).
- `delivery_attempts`: 3 неудачные доставки → статус `failed` (запись остаётся для отладки).
- Rate limit на `request-otp`: не чаще 1 SMS в 60 сек на связку `phone` / `device_id`; дополнительно максимум N SMS в час на один телефон. Проверка — по последним записям `sms_outbox`.

## Идентификация устройства клиента

В `request-otp` пользователь ещё не авторизован, поэтому бекенд не может надёжно определить устройство/пользователя. Принятое решение: клиент один раз генерирует `uuid`, хранит в `localStorage` и шлёт его в теле запроса полем `device_id`. Бекенд использует его (вместе с `phone`) для rate limit.
